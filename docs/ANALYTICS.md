# Lastro Analytics

Branch `codex/lastro-analytics`; sem deploy ou migration em produção. Homologação usa somente o Worker `lastro-ecosystem-staging` e seu D1 existente. Migration `0009_analytics.sql` aplicada apenas nesse staging. Nenhum cron, recurso pago ou conta de faturamento adicionado.

Google Cloud: projeto `project-0472db88-3d1b-4340-925`, propriedade `560757639`, API ativada. Conta de serviço existente ativa, Leitor sem métricas financeiras; política de bloqueio de chaves preservada. OAuth externo em teste, proprietário autorizado, somente `analytics.readonly`. Cliente Web `Lastro Analytics — Worker` criado; callback exato `https://lastro-ecosystem-staging.marioserafim-da.workers.dev/api/analytics/oauth/callback`. Branding: nome, e-mails, página inicial e domínio próprio configurados; logo e documentos públicos não foram inventados. A chave inicial foi desativada após uma leitura da interface incluí-la no retorno da ferramenta; a substituta não foi exposta.

Fluxo de provisionamento: proprietário autenticado abre `/api/analytics/oauth/connect` e concede leitura no Google. State, nonce HttpOnly e PKCE duram dez minutos; callback consome state uma única vez. O download contém somente código de autorização curto e verifier PKCE, nunca access/refresh token ou client secret. O operador executa `node --import tsx scripts/configure-analytics.ts <arquivo-cliente> <arquivo-autorizacao>`; o script troca o código em memória, instala os dois Secrets no Worker de staging, remove os arquivos temporários e testa os dois relatórios. Nenhum token persistido em D1, Git ou navegador. Não passar credenciais literais em argumentos. O cliente baixado fica temporariamente no diretório ignorado `.wrangler/analytics-bootstrap`, com ACL restrita ao proprietário/SYSTEM, somente durante provisionamento. O client ID já é uma variável pública no config; não tentar sobrescrevê-la como Secret no mesmo deploy.

Configuração: `ANALYTICS_ENABLED`, `GA4_PROPERTY_ID`, `GOOGLE_OAUTH_CLIENT_ID`; Secrets `GOOGLE_OAUTH_CLIENT_SECRET`, `GA4_REFRESH_TOKEN`. `/api/analytics/overview` conserva a autenticação Lastro, cache agregado de doze horas e backoff de uma hora; lease protege contra chamadas concorrentes. Consulta sete dias completos por date e pagePath, limita páginas a cem e filtra caminhos não editoriais para evitar dados pessoais. Informa snapshots antigos, truncamento, dados vazios e erros sanitizados. Não soma usuários diários como usuários únicos semanais.

Em teste externo, refresh tokens expiram em sete dias ([Google](https://developers.google.com/identity/protocols/oauth2#expiration)). Operação contínua exige avaliar publicação para uso pessoal, exceção de verificação, aviso de app não verificado e limite de usuários; não publicado automaticamente. Revogação/expiração exige nova autorização. Não substituir por chave de serviço nem desativar política. Para produção: autorização de deploy, backup/migration 0009, callback próprio implementado/implantado e provisionamento explícito dos Secrets; manter flag desativada até validar. Desativar flag interrompe consultas sem afetar o ecossistema.

Renovação de access token pelo Worker e duas consultas autenticadas ao overview passaram; mesmo `fetchedAt`, cache válido por doze horas, consulta sem sessão 401. Secrets de staging `GOOGLE_OAUTH_CLIENT_SECRET` e `GA4_REFRESH_TOKEN` configurados; arquivos temporários de cliente e autorização removidos. Evidências agregadas em `.wrangler/analytics-first-report.json` e `analytics-remote-verification.json`, ignorados pelo Git. Oito testes direcionados, TypeScript backend/frontend e builds passaram. Erros 401/403/429 e respostas vazias validados por injeção local, sem esgotar cotas reais. Corrigida incompatibilidade comprovada de workerd com `redirect:error`: modo `manual`, respostas 3xx recusadas sem encaminhar credenciais. Limites de referência: [Data API](https://developers.google.com/analytics/devguides/reporting/data/v1/quotas).
